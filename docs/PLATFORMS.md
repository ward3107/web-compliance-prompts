# Website platform routes

The studio has one shared banner runtime and a platform-specific delivery route.
Open `platforms.html` to inspect the route before entering business details.
The selector, guides and setup work in English/Hebrew, including the offline ZIP.
An unknown platform is never silently treated as WordPress or a working install.

| Platform | Delivery in this release | Still needs destination-site verification |
| --- | --- | --- |
| WordPress / WooCommerce | Existing uploadable WordPress plugin | Actual plugins, theme, checkout, tags and consent wiring |
| HTML / PHP / custom website | Four runtime files and an HTML snippet | Shared layout, asset paths, CSP and tracker wiring |
| React / Vite, Vue / Vite | Five runtime files and a shared-document loader example | Production build, route changes, asset paths and tracker wiring |
| Next.js | Five runtime files and a root `next/script` example | Router version, hydration, basePath, CSP and tags |

| Astro | Five runtime files and an unbundled shared-layout example | ClientRouter/view transitions can replace the body; a dedicated lifecycle adapter is not included |

## Framework loader

`mount-banner.js` is generated by the existing dependency-free installer. Serve
it alongside `cookie-consent.css`, `theme.css`, `cookie-consent.js` and `install.js`.
Load only this entry point from the persistent root layout. It waits for the DOM,
loads styles in order and then the widget before its configured installer. Asset
URLs resolve relative to the loader's URL, including subdirectory deployments.
Repeated execution shares a promise and does not add a second preferences button.
It does not install or control third-party trackers. Keep non-essential tracking
disabled until the site's consent integration permits it.

The bootstrap emits `compliance:installation-ready` only after its scripts and
preferences button initialize. Failure emits `compliance:installation-error` and
allows a later explicit retry. These events describe local component loading,
not consent enforcement, a completed site scan or customer acceptance.

HTML snippets, `next/script`, `useHead` and the other examples are integration
references. Browser runtime tests do not establish that a real framework project
builds or that an authenticated hosted platform accepts the code. A router that
replaces the document body needs its own lifecycle handling.

## Honest handoff

Every downloaded installation includes `PLATFORM.json` with the chosen route,
documentation references and `not_tested` customer/framework/tracker states.
Hosted-platform plan ZIPs contain instructions and status only: no runtime,
fake native connector, pixel-control promise or executable embed snippet.
Existing saved projects using `wordpress`, `other` or `unknown` still load.
Unknown-platform projects can save drafts and legal-review packets; installation
download waits until the platform is identified.

Use the kit's `ACCEPTANCE.html` worksheet to record first visit, rejection,
granular choice, withdrawal, reload, keyboard, screen-reader, mobile, RTL,
policy-link, update, rollback and removal evidence. No checks start as passed.
Document generation remains Hebrew and Israel-only; platform selection does not
expand jurisdiction coverage or provide legal approval.
